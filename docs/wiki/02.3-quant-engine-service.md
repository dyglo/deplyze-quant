# 2.3 Quant Engine Service

> `deplyze-quant-engine` is a **separate** Cloud Run service from the
> Express gateway. It is the autonomous quantitative intelligence
> infrastructure introduced in V3 Phase 2: ingestion, refinement,
> feature engineering, artifact / observation persistence, and
> briefing generation. It writes to BigQuery; the gateway reads.

---

## 2.3.1 Service shape

| Property | Value |
|---|---|
| Name | `deplyze-quant-engine` |
| Runtime | Python 3.11 |
| Framework | FastAPI |
| Version | `3.0.0` |
| Region | `us-central1` |
| Registry | `us-central1-docker.pkg.dev/deplyze-quant/deplyze-quant-engine` |
| Auth | Cloud Run service-to-service IAM (`scheduler-invoker` SA invokes; gateway SA invokes for on-demand triggers) |
| Source | `services/quant-engine/` |
| Entrypoint | `services/quant-engine/app/main.py` |
| Container CMD | `uvicorn app.main:app --host 0.0.0.0 --port 8080` |

The engine is **deployed separately** from `deplyze-gateway` and is
invoked by:

- **Cloud Scheduler** — 10 V3P2 jobs on a fixed cron.
- **Internal Cloud Run Jobs** — manual backfills and one-offs.
- **The gateway** — optionally, for on-demand pipeline triggers.

Authentication is GCP IAM (OIDC identity tokens). Secrets
(`EDGAR_USER_AGENT`, `FRED_API_KEY`, etc.) are passed as Cloud Run
environment variables — never embedded in source.

## 2.3.3 Lifespan management

`app/main.py` uses FastAPI's `lifespan` async context manager:

```python
@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    log.info("quant_engine.startup", env=settings.QUANT_ENGINE_ENV,
             project=settings.GCP_PROJECT_ID)
    try:
        client = get_bigquery_client()
        datasets = list(client.list_datasets(project=settings.GCP_PROJECT_ID))
        log.info("bigquery.connected",
                 datasets=[ds.dataset_id for ds in datasets])
    except Exception as exc:
        log.error("bigquery.connection_failed", error=str(exc))
        # Don't sys.exit — let /ready reflect the failure
    log.info("quant_engine.ready")
    yield
    log.info("quant_engine.shutdown")
```

Startup:

1. Validates BigQuery connectivity (light probe — `list_datasets`).
2. Logs the connected datasets.
3. Critically logs in production if BigQuery is unavailable, but
   **does not exit** — `/ready` will report `503` and Cloud Run will
   refuse to send traffic until the probe succeeds.

Shutdown logs a `quant_engine.shutdown` event.

A global exception handler converts unhandled errors to a uniform
`500 / {"error":"Internal Server Error","code":"INTERNAL_ERROR"}` JSON
response and logs the path + traceback through structlog.

## 2.3.4 Routers and endpoints

Three routers are mounted in `main.py`:

```python
app.include_router(health_router,     tags=["Health"])
app.include_router(pipelines_router,  prefix="/pipelines", tags=["Pipelines"])
app.include_router(warehouse_router,  prefix="/warehouse", tags=["Warehouse"])
```

When invoked behind Cloud Run the canonical paths look like
`POST /v1/pipelines/ingest/edgar` etc. (the `/v1` prefix is applied by
Cloud Run path-based routing); inside the FastAPI app the paths are
`/pipelines/...`.

In non-production environments, FastAPI also serves `/docs` (Swagger)
and `/redoc`.

### Health (`app/api/health.py`)

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | Liveness — always 200 if the process is running. Returns `{ok, service, version}`. |
| `GET` | `/ready` | Readiness — checks BigQuery connectivity. Returns 200 if connected, 503 otherwise. |
| `GET` | `/version` | Service version (`3.0.0`). |
| `GET` | `/bq-status` | Detailed BigQuery connectivity / dataset listing. |

`/ready` is the canonical Cloud Run readiness probe target. It is
backed by `bigquery/client.check_connectivity()`.

### Pipelines (`app/api/pipelines.py`)

Pipeline orchestration. **15+ endpoints**. Each endpoint is a thin
shim that:

1. Validates the Pydantic request model.
2. Creates a `run_id` (UUID) and registers it in the in-process `_runs`
   dict.
3. Hands the actual work to `BackgroundTasks` so the HTTP response
   returns immediately with `{run_id, status: "queued", ...}`.
4. The background task updates `_runs[run_id]` as it progresses.

| Method | Path | Wave | Purpose |
|---|---|---|---|
| `POST` | `/ingest` | V3P1 | Generic provider ingestion (`run_ingest`). |
| `POST` | `/refine` | V3P1 | Normalise / deduplicate raw → cleaned. |
| `POST` | `/features` | V3P1 | Compute features from cleaned data. |
| `POST` | `/artifacts` | V3P1 | Generate artifacts from features. |
| `POST` | `/daily-run` | V3P1 | Full pipeline (ingest → refine → features → artifacts). |
| `POST` | `/backfill` | V3P1 | Historical backfill over a date range. |
| `POST` | `/ingest/edgar` | **V3P2 B** | SEC EDGAR filings ingestion. Requires `EDGAR_USER_AGENT`. |
| `POST` | `/ingest/fred` | **V3P2 C** | FRED macro / yield ingestion. Writes `public_macro_raw` + `macro_cleaned`. |
| `POST` | `/ingest/cot` | **V3P2 D** | CFTC Commitment of Traders. |
| `POST` | `/ingest/rss` | **V3P2 D** | RSS / Atom feed ingestion. |
| `POST` | `/ingest/calendar` | **V3P2 D** | Economic-release calendar (FRED-backed). |
| `POST` | `/refine/documents` | **V3P2 E** | Parse unprocessed `document_sources_raw` rows. |
| `POST` | `/refine/entities` | **V3P2 F** | Extract ontology features from parsed docs. |
| `POST` | `/intelligence/macro-regime` | **V3P2 G** | Liquidity/inflation/rates/growth regimes. |
| `POST` | `/intelligence/narratives` | **V3P2 H** | Theme lifecycle + emergence. |
| `POST` | `/briefings/generate` | **V3P2 K** | Daily / weekly / anomaly briefings. |
| `GET` | `/status/{run_id}` | — | Get status / summary of a pipeline run. |

Request bodies — see `app/api/pipelines.py` for the full Pydantic
models. Examples:

```python
class EdgarIngestRequest(BaseModel):
    symbols_or_ciks: List[str]
    days_back: Optional[int] = None
    forms: Optional[List[str]] = None

class FredIngestRequest(BaseModel):
    series_ids: Optional[List[str]] = None     # defaults to DEFAULT_SERIES
    since_date: Optional[str] = None           # YYYY-MM-DD
    days_back: int = 1825                      # 5y default

class BriefingsRequest(BaseModel):
    briefing_types: Optional[List[str]] = None  # subset of three types
```

#### Run registry

Each pipeline tracks a run in `_runs`:

```python
{
    "run_id": "...",
    "pipeline_name": "edgar_filings_ingest",
    "status": "queued|running|completed|completed_with_errors|failed",
    "started_at": "<iso>",
    "completed_at": "<iso|null>",
    "records_processed": 0,
    "artifacts_generated": 0,
    "errors": [],
    # plus pipeline-specific fields (e.g. themes_tracked, briefings_written)
}
```

`GET /pipelines/status/{run_id}` returns this object. The registry is
**process-scoped** today; persistent run history is a planned next step
(write to a `model_runs` BigQuery table).

### Warehouse (`app/api/warehouse.py`)

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/warehouse/provision` | Idempotently create all V3 BigQuery tables. Safe to call repeatedly. |
| `GET` | `/warehouse/tables` | List tables that exist in the configured datasets. |

`provision` returns:

```json
{
  "ok": true,
  "summary": { "created": 0, "already_existed": 12, "errors": 0 },
  "details": { "created": [...], "exists": [...], "errors": [] }
}
```

This is the runtime equivalent of `python provision_bq.py` — useful
when bringing up a fresh environment without local Python.

## 2.3.5 Configuration

All settings live in `app/core/config.py` (Pydantic). Required env vars
in production:

| Env var | Purpose |
|---|---|
| `GCP_PROJECT` / `GCP_PROJECT_ID` | BigQuery project id. |
| `QUANT_ENGINE_ENV` | `production` / `staging` / `local`. |
| `BQ_DATASET_RAW_API` | Default `raw_api`. |
| `BQ_DATASET_RAW_PUBLIC` | Default `raw_public`. |
| `BQ_DATASET_RAW_DOCS` | Default `raw_documents`. |
| `BQ_DATASET_CLEANED` | Default `cleaned`. |
| `BQ_DATASET_FEATURES` | Default `features`. |
| `BQ_DATASET_RESEARCH` | Default `research`. |
| `BQ_DATASET_ARTIFACTS` | Default `artifacts`. |
| `BQ_DATASET_MODEL_OUT` | Default `model_outputs`. |
| `EDGAR_USER_AGENT` | **Required** for Wave B (SEC fair-use). |
| `FRED_API_KEY` | **Required** for Wave C / Calendar. |
| `ALLOWED_ORIGINS` | CORS allow-list (internal GCP origins in prod). |

CORS is restricted to internal origins (`allow_credentials=False`,
methods limited to `GET, POST`). No browser ever calls the quant engine
directly — only the gateway and Scheduler.

## 2.3.6 Deployment

### Container build & deploy

```bash
# From repo root
bash services/quant-engine/deploy.sh
```

`deploy.sh` builds the image, pushes to
`us-central1-docker.pkg.dev/deplyze-quant/deplyze-quant-engine`, and
runs `gcloud run deploy deplyze-quant-engine` in `us-central1`, with
service-to-service auth enforced (no `--allow-unauthenticated`).

Tunables in `deploy.sh`:

- `--memory 1Gi` (bump to `2Gi` if document parsing OOMs)
- `--cpu 1` (bump to `2` if needed)
- `--timeout 540` (max 9 minutes per request — keep heavy work in
  background tasks; the HTTP response always returns quickly)
- `--concurrency 4` (small — background work + BigQuery clients per
  request)

### BigQuery provisioning

```bash
# Option A — preferred
cd services/quant-engine
python provision_bq.py

# Option B — raw SQL fallback (no Python deps required)
PROJECT_ID=deplyze-quant
sed "s/{PROJECT_ID}/${PROJECT_ID}/g" \
    migrations/v3p2/001_wave_a_schemas.sql \
  | bq query --project_id="${PROJECT_ID}" \
             --use_legacy_sql=false --nouse_cache
```

Both paths are **idempotent**. Re-runs are a no-op for tables that
already exist.

### Cloud Scheduler provisioning

```bash
bash services/quant-engine/deploy/v3p2/schedulers.sh
```

Creates the ten V3P2 jobs (see [§13 in the Platform Overview](./01-platform-overview.md#13-infrastructure-overview)).
Idempotent — re-running won't recreate existing jobs.

### Verifying

```bash
SERVICE_URL=$(gcloud run services describe deplyze-quant-engine \
  --region us-central1 --format 'value(status.url)')
TOKEN=$(gcloud auth print-identity-token)

# Liveness
curl "$SERVICE_URL/health" -H "Authorization: Bearer $TOKEN"

# Readiness — must be 200 once BigQuery is reachable
curl -i "$SERVICE_URL/ready" -H "Authorization: Bearer $TOKEN"

# Provision (safe to run anytime)
curl -X POST "$SERVICE_URL/warehouse/provision" \
  -H "Authorization: Bearer $TOKEN"
```

### On-demand pipeline trigger

```bash
curl -X POST "$SERVICE_URL/pipelines/ingest/edgar" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"symbols_or_ciks":["AAPL","MSFT","NVDA"],"days_back":365}'
# → { "run_id": "<uuid>", "status": "queued", ... }

curl "$SERVICE_URL/pipelines/status/<uuid>" \
  -H "Authorization: Bearer $TOKEN"
# → full run summary
```

## 2.3.7 Failure modes & diagnostics

| Symptom | Cause | Fix |
|---|---|---|
| `/ready` returns 503 | BigQuery unreachable / IAM missing | Check service account roles (`bigquery.dataEditor`, `bigquery.user`) on each V3P2 dataset. |
| `EDGAR_USER_AGENT is not configured` | env var missing | Set `EDGAR_USER_AGENT` in Cloud Run; redeploy. |
| `FRED_API_KEY required` | env var missing | Set `FRED_API_KEY`; redeploy. |
| EDGAR `429 Too Many Requests` | SEC rate-limit | Client backs off with 5s + tenacity retry. If persistent, verify the User-Agent specifies a real contact. |
| FRED `429` | over budget | Reduce `series_ids` or `days_back`. Engine self-throttles to ~60/min vs 120/min ceiling. |
| `document_parse` reports 0 written | mass extraction failure | Run with `{"limit":10}` and inspect `extraction_method` in `parsed_documents_raw`. |
| `entity_features` reports 0 written | all docs `extraction_quality < 0.3` | Lower the quality floor in `entity_features.py::_select_unprocessed`, or improve the parser. |
| `macro_regime` returns "no macro data" | `macro_cleaned` empty | Run `/pipelines/ingest/fred` first. |
| `narratives` returns "0 themes tracked" | no theme entities in `ontology_features` | Run document parse + entity extraction first; narratives only emerge from text. |
| OOM at parse time | memory ceiling | Bump `--memory` to `2Gi` in `deploy.sh` and redeploy. |

Inspect logs:

```bash
gcloud logging read \
  "resource.type=cloud_run_revision AND \
   resource.labels.service_name=deplyze-quant-engine AND \
   severity>=ERROR" \
  --limit 50
```

## 2.3.8 Relationship to the gateway

| Concern | Gateway (`deplyze-gateway`) | Quant Engine (`deplyze-quant-engine`) |
|---|---|---|
| Language | TypeScript / Express | Python / FastAPI |
| Auth | Firebase ID token (user) | GCP IAM (service-to-service) |
| Caller | Browser (web app) | Cloud Scheduler, gateway, manual operators |
| Writes BigQuery? | No | Yes |
| Reads BigQuery? | Yes (V3P2 router) | Yes |
| Computes intelligence? | No (V3P2) | Yes |
| Owns provider keys? | Front-of-house keys (Finnhub, AV, TwelveData, Tavily, Serper, Gemini) | Back-of-house ingestion keys (FRED, EDGAR UA, CFTC, RSS, Calendar) |

Both run on Cloud Run, both in `us-central1`, but they are independent
services with independent deploy lifecycles. The gateway never blocks
on the engine — the engine has already written before the gateway
reads.
