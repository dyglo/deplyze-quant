# 3.4 BigQuery Data Warehouse

> The BigQuery refinery is the system of record for all market and
> intelligence data in Deplyze Quant. V3 Phase 2 adds 12 new tables on
> top of the V3 Phase 1 base, organised across four logical zones —
> **raw**, **cleaned**, **features**, **research/artifacts/model
> outputs** — with strict lineage and partitioning.

---

## 3.4.1 Project & dataset layout

All data lives in the `deplyze-quant` GCP project. Dataset names are
configurable via env vars but default to:

| Logical zone | Dataset(s) | Purpose |
|---|---|---|
| **Raw** | `raw_api`, `raw_public`, `raw_documents` | Exact source data, immutable, lineage-tagged. |
| **Cleaned** | `cleaned` | Normalised, deduplicated, source-agnostic. |
| **Features** | `features` | ML-ready engineered features (returns, z-scores, ontology, narrative). |
| **Research** | `research` | Persisted intelligence: observations, memory, briefings. |
| **Artifacts** | `artifacts` | Event-shaped artifacts for the intelligence timeline. |
| **Model outputs** | `model_outputs` | Model prediction / scoring output tables. |

The web app's **Warehouse Explorer** maps these GCP datasets into four
analyst-facing "zones": `dq_raw`, `dq_intelligence`, `dq_research`,
`dq_features` — see [11.2 Warehouse Explorer](./11.2-warehouse-explorer.md).


## 3.4.2 Lineage envelope

Every row in every V3P2 table carries the same lineage envelope on top
of its domain-specific columns:

| Column | Type | Purpose |
|---|---|---|
| `id` | `STRING NOT NULL` | Row UUID. |
| `symbol` | `STRING` | Asset symbol, if applicable. |
| `asset_type` | `STRING` | `equity` / `etf` / `macro` / `narrative` / `filing` … |
| `provider` | `STRING` | `fred`, `sec_edgar`, `cftc`, `rss`, `deplyze_quant`. |
| `source_url` | `STRING` | Original URL pulled. |
| `source_type` | `STRING` | Domain label (e.g. `narrative_observation`). |
| `ingestion_time` | `TIMESTAMP NOT NULL` | When we wrote it. |
| `observation_time` | `TIMESTAMP` | When the event happened. Used for partitioning. |
| `processing_time` | `TIMESTAMP` | When the pipeline produced this row. |
| `data_quality_score` | `FLOAT64` | `[0, 1]`. |
| `lineage_id` | `STRING` | Stable, replayable identifier. |
| `confidence` | `FLOAT64` | `[0, 1]`. |
| `metadata` | `JSON` | Free-form provenance. |
| `created_at` | `TIMESTAMP NOT NULL` | First write timestamp. |
| `updated_at` | `TIMESTAMP` | Last write timestamp. |

Artifact tables (`*_artifacts`) carry a different envelope tailored to
event-shaped data — `artifact_id`, `artifact_type`, `evidence`,
`metrics`, `severity`, `source_tables`, `lineage_id`, `is_test`. The
contract is the same: every row is **fully traceable** to its inputs.

## 3.4.3 V3P2 table reference (Wave A)

The canonical DDL is in
`services/quant-engine/migrations/v3p2/001_wave_a_schemas.sql`. The
Python provisioner (`provision_bq.py`) keeps `app/bigquery/schemas.py`
as the source of truth and applies it idempotently. All 12 tables use
`CREATE TABLE IF NOT EXISTS` — re-running the migration is a no-op.

### `cleaned.filings_cleaned`

Normalised SEC filings, one row per accession.

| Column | Type | Notes |
|---|---|---|
| _lineage envelope_ | — | see §3.4.2 |
| `cik` | `STRING` | SEC central index key. |
| `accession_number` | `STRING` | Filing accession. |
| `form_type` | `STRING` | `10-K`, `10-Q`, `8-K`, … |
| `filing_date` | `DATE` | **Partition key.** |
| `period_of_report` | `DATE` | Reporting period end. |
| `entity_name` | `STRING` | Filer name. |
| `primary_document_url` | `STRING` | Canonical filing URL. |
| `primary_document_mime` | `STRING` | `text/html`, `application/pdf`, … |
| `related_symbols` | `ARRAY<STRING>` | Tickers tied to the filer. |
| `themes` | `ARRAY<STRING>` | Tagged themes (joined from `ontology_features`). |
| `is_amended` | `BOOL` | `/A` filings. |
| `dedup_hash` | `STRING` | Idempotency hash. |

- **PARTITION BY** `filing_date`
- **CLUSTER BY** `cik, form_type`

|---|---|---|

### `research.generated_briefings`

Briefings inherit the shared research envelope plus:

| Column | Type | Notes |
|---|---|---|
| `briefing_type` | `STRING` | `daily_market_intelligence` / `weekly_regime_brief` / `anomaly_summary`. |

gateway via `ROW_NUMBER() OVER (PARTITION BY briefing_type ORDER BY
observation_time DESC)`.

## 3.4.4 Partitioning & clustering conventions

| Pattern | Used for | Why |
|---|---|---|
| Partition on `observation_time` | features, observations, narrative_cleaned | Reads always filter by date; lets the query planner prune. |
| Partition on `filing_date` | filings, filing_features | Filings are queried by filing date, not by `observation_time`. |
| Partition on `created_at` | artifacts | Artifacts are append-only events; `created_at` is the natural axis. |
| Partition on `DATE(last_seen_at)` | narrative_memory | Memory is rewritten on every run; partition by recency. |
| Cluster on `(series_id)` / `(theme_id)` / `(entity_type, entity_id)` / `(cik, form_type)` | features / research | Aligns with the most common WHERE clauses. |
| Cluster on `(artifact_type)` / `(artifact_type, symbol)` | artifacts | Gateway reads filter by artifact_type, often joined by symbol. |

This combination keeps single-day reads (the dominant V3P2 access
pattern) under typical Cloud Run BigQuery quota.

## 3.4.5 Provisioning

Two paths, both **idempotent**:

```bash
# Preferred — Python provisioner uses schemas.py as source of truth
cd services/quant-engine
python provision_bq.py

# Fallback — pure-SQL provisioner (no Python deps required)
PROJECT_ID=deplyze-quant
sed "s/{PROJECT_ID}/${PROJECT_ID}/g" \
    migrations/v3p2/001_wave_a_schemas.sql \
  | bq query --project_id="${PROJECT_ID}" \
             --use_legacy_sql=false --nouse_cache
```

The runtime equivalent is `POST /warehouse/provision` on the quant
engine (see [2.3 Quant Engine Service](./02.3-quant-engine-service.md)):

```bash
SERVICE_URL=$(gcloud run services describe deplyze-quant-engine \
  --region us-central1 --format 'value(status.url)')
TOKEN=$(gcloud auth print-identity-token)
curl -X POST "$SERVICE_URL/warehouse/provision" \
  -H "Authorization: Bearer $TOKEN"
```

Use whichever fits the moment — the result is identical and
re-runnable.

## 3.4.6 Gateway read surface

V3P2 reads live in `cloud-run/gateway/src/routes/v3p2.ts`. The router
is mounted at `/v1` after the existing routers so it fills in the new
paths only:

| Endpoint | BigQuery source | Cache TTL |
|---|---|---|
| `GET /v1/macro/regimes` | `research.macro_observations` (latest per `observation_type`, 30d window) | `TTL.quote * 10` |
| `GET /v1/filings/recent` | `cleaned.filings_cleaned` | `TTL.quote * 4` |
| `GET /v1/filings/:id` | `cleaned.filings_cleaned` + `research.filing_observations` | `TTL.quote * 4` |
| `GET /v1/narratives/themes` | `research.narrative_memory` | `TTL.quote * 5` |
| `GET /v1/narratives/recent` | `cleaned.narrative_cleaned` | `TTL.quote * 5` |
| `GET /v1/research/macro-observations` | `research.macro_observations` | `TTL.quote * 5` |
| `GET /v1/relations/context` | join of `macro_observations` + `narrative_memory` + `filing_observations` | `TTL.quote * 5` |
| `GET /v1/briefings/latest` | `research.generated_briefings` (dedup latest per `briefing_type`) | `TTL.quote * 5` |

All routes use the gateway's `withCache(key, ttl, () => runQuery(...))`
primitive, so a warmed Redis cache short-circuits most reads.
