# 11.1 Model Observatory

> An honest, code-driven view of every ML model on the platform.
> Each model declares its dependencies (providers, datasets), its
> required validation, and its **status** — `data-ready`,
> `needs-training`, `needs-dataset`, `planned`, or `disabled` — so
> analysts know exactly what's running, what's blocked, and what's
> on the roadmap.

Source: `src/pages/ModelObservatory.tsx` (255 lines).

---

## 11.1.1 Surface

The Model Observatory page renders three sections:

1. **Status summary** — counts of models grouped by status.
2. **Model table** — sortable list of models, ranked by status
   (`data-ready` first, `disabled` last), with provider availability.
3. **Detail drawer** — clicking any row opens a drawer showing
   purpose, expected output, features, required providers / datasets,
   validation criteria, and the next implementation step.

A `Run diagnostics` button refreshes provider health via
`/v1/providers/health` so each model card can flag which of its
required providers are connected.

---

## 11.1.2 Status taxonomy

```ts
type ModelStatus =
  | 'data-ready'      // dataset + providers wired; can train / ship now
  | 'needs-training'  // dataset present but model not yet trained
  | 'needs-dataset'   // model design ready, blocked on BigQuery datasets
  | 'planned'         // designed but not started
  | 'disabled'        // intentionally off (e.g. cost / quality)
```

Ranking order (`STATUS_RANK`) ensures `data-ready` models appear at the
top of the table:

```ts
const STATUS_RANK: Record<ModelStatus, number> = {
  'data-ready': 0, 'needs-training': 1, 'needs-dataset': 2, 'planned': 3, 'disabled': 4,
};
```

## 11.1.4 Diagnostics

The page uses `useProviderHealth` (which talks to
`/v1/providers/health` on the gateway) and `checkModelAvailability` to
flag, per model, whether **all** required providers are connected:

- ✅ "all connected" — green check.
- ⚠ "needs: <provider list>" — amber warning when at least one
  required provider is unconfigured server-side.

The `Run diagnostics` button calls `health.refresh()` so analysts can
re-verify after IAM / secret changes without reloading the page.

---

## 11.1.5 Reading the registry as a roadmap

The registry doubles as a documented roadmap:

- **`data-ready`** rows are the next implementation targets — the
  data is there; the model just needs to be trained / shipped.
- **`needs-dataset`** rows are blocked on the warehouse explorer's
  `planned` rows (most often `dq_features.returns`,
  `dq_features.volatility`, `dq_features.correlations`,
  `dq_cleaned.economic_events`).
- **`planned`** rows are designed but un-started.
- **`disabled`** rows are conscious decisions, not omissions.

The `nextStep` field on every model is the single source of truth for
"what unblocks this one." Updates land in `MODELS` directly.
