# 11.2 Warehouse Explorer

> The platform's live registry of BigQuery datasets, the provider mesh
> that feeds them, and the intelligence artifacts they produce. The
> page is the analyst-facing mirror of [3.4 BigQuery Data Warehouse](./03.4-bigquery-data-warehouse.md).

Source: `src/pages/WarehouseExplorer.tsx` (664 lines).

---

## 11.2.1 Layout

The Explorer is organised around four analyst-facing **zones**, each
mapping onto one or more BigQuery datasets in the underlying refinery:

| Zone (UI) | Hint | BigQuery datasets behind it |
|---|---|---|
| **`dq_raw`** — Raw Data | Exact source data, immutable | `raw_api`, `raw_public`, `raw_documents` |
| **`dq_intelligence`** — Intelligence | AI-synthesised artifacts and model outputs | `artifacts`, `model_outputs` |
| **`dq_research`** — Research | Persisted briefings, insights, lab sessions | `research`, Firestore subset |
| **`dq_features`** — Feature Layer | ML-ready engineered features | `features` (planned tables) |

Each dataset row carries provider, cadence, schema, quality notes, and
a **wiring status**:

- `wired` — populated and queried by the platform today.
- `partial` — present but partially populated / partially queried.
- `planned` — designed; not yet ingesting.

## 11.2.3 Provider routing map

Each domain has a documented **fallback chain** so analysts can see at
a glance which provider serves a request and which providers are the
backup. Pulled from `ROUTING_DOMAINS`:

| Domain | Chain (primary → fallback) |
|---|---|
| Quotes | `polygon → finnhub → twelve_data` |
| OHLCV | `eodhd → twelve_data → fmp → alpha_vantage` |
| Fundamentals | `fmp → finnhub → eodhd` |
| News | `polygon → finnhub → tavily → serper` |
| Earnings | `fmp → finnhub → eodhd` |
| Macro | `alpha_vantage` |
| Research | `tavily → serper → gemini` |
| Filings | `edgar` |

The Routing tab on the Explorer renders this as a row per domain, with
each provider chip coloured by its live `/v1/providers/health` state
(green operational, amber degraded, grey not configured).

In V3P2 the engine's own provider mesh (FRED, EDGAR with
`EDGAR_USER_AGENT`, CFTC, RSS, Calendar) is exposed through Scheduler
jobs rather than user-facing routes, so it doesn't appear in the
routing map — but it does show up in the dataset registry above
through the `raw_public.*` tables it populates.

## 11.2.4 Artifact archive

The Explorer embeds a `QuantArchivePanel` that lists recent
intelligence artifacts pulled via `useArtifacts`. Clicking an artifact
opens `ArtifactDetailDrawerBody`, which shows:

- Title, summary, body (markdown).
- Symbol / related symbols / tags.
- Evidence + metrics (JSON).
- Source tables — the FQNs of the BigQuery tables the artifact was
  built from.
- Lineage id — for replay.

Because V3P2 emits artifacts to typed tables
(`artifacts.macro_artifacts`, `narrative_artifacts`,
`filing_artifacts`) and observation tables
(`research.macro_observations`, `narrative_memory`,
`filing_observations`), the archive surface now covers the platform's
own deterministic intelligence alongside any user-generated artifacts.

## 11.2.5 How dataset status changes

- **`planned` → `partial`** when the first row lands in a table.
- **`partial` → `wired`** when:
  1. The table is partitioned and clustered per the conventions in
     [§3.4.4](./03.4-bigquery-data-warehouse.md#344-partitioning--clustering-conventions).
  2. The Scheduler job that populates it is `ENABLED`.
  3. A gateway route reads from it.

Promotion happens by editing `DATASETS` in `WarehouseExplorer.tsx`.
Future iterations will lift `DATASETS` into the engine's
`/warehouse/tables` endpoint so the page becomes fully data-driven
instead of declarative.
